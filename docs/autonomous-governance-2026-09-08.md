# QtMinecraft 自主连续开发治理机制

日期：2026-09-08
版本：1.0
状态：持续开发治理规则
适用对象：GLM5.3Flash 主开发 Agent、周期性治理审计 Agent、未来替换的其他代码 Agent

本文档的目的不是再写一份功能计划，而是规定：

- Agent 什么时候必须重新检查大方向；
- 检查哪些证据；
- 什么问题可以自动修复；
- 什么问题必须暂停；
- 任务做完多少个后如何触发治理；
- API 断链后如何恢复；
- 如何防止 Agent 一直工作但方向已经跑偏。

---

## 1. 机制总览

QtMinecraft 使用两层循环：

    第一层：Execution Loop
      当前任务 → 实现 → 测试 → 阴性轮 → 文档 → Git 提交 → 下一任务

    第二层：Governance Loop
      每 5 个完成任务 / 每批次结束 / 每周定时
      → 读取本治理文档
      → 检查方向、质量、架构、状态
      → 自动修复允许修复的问题
      → 创建纠偏任务或进入 NEEDS_HUMAN
      → 继续 Execution Loop

第一层负责“把任务做完”，第二层负责“确认一直在做正确的任务”。

### 1.1 永不停止的准确含义

本机制中的“永不停止”表示：

- Agent 不因为一个任务完成就丢失下一步；
- Agent 不因为 API 断链就丢失上下文；
- Agent 不因为文档过长就无法恢复；
- Agent 不因为单次构建或测试失败就无限乱改；
- Agent 可以跨越多个会话、多个 Agent 和多个模型继续工作；
- 每次停止都留下明确恢复点；
- 有新的 READY 任务时自动继续。

它不表示：

- 绕过 API 限额；
- 绕过操作系统、进程或网络故障；
- 无限重试同一个根因；
- 自动改变产品目标；
- 自动批准不可逆的数据迁移；
- 自动删除用户工作区修改；
- 自动把自己的判断当成最终产品验收。

真正长期稳定的系统必须能够安全停止，然后可靠恢复。

## 2. 持久化记忆层级

Agent 不能依赖上一轮聊天上下文。所有可恢复信息必须落在以下位置：

| 优先级 | 文件或来源 | 保存内容 |
|---|---|---|
| 1 | docs/agent-state.md 或 dev-plan 顶部控制块 | 当前任务和当前恢复点 |
| 2 | docs/agent-continuation-prompt-2026-09-08.md | Agent 固定工作规则 |
| 3 | docs/dev-plan.md | 任务账本、需求、历史证据 |
| 4 | docs/refactor-plan-2026-09-08.md | 长期架构方向 |
| 5 | docs/autonomous-governance-2026-09-08.md | 周期审计和纠偏规则 |
| 6 | Git history | 实际实现历史 |
| 7 | 测试和构建日志 | 可验证事实 |
| 8 | 当前工作区 | 未提交现场 |

规则：

- 控制块保存当前状态，不保存长篇历史；
- dev-plan 保存任务历史，不作为每轮全量输入；
- refactor-plan 作为架构参考，按章节读取；
- 本治理文档作为稳定规则，不由普通任务随意修改；
- 治理文档的修改必须形成独立 docs 提交，并带日期和原因。

## 3. 触发条件

### 3.1 按任务数量触发

每完成 5 个任务，必须执行一次治理审计。

这里的“完成任务”只计算已经满足以下条件的任务：

- fix 或等价实现已经提交；
- test 或等价验证已经提交；
- docs 已回标；
- 任务状态为 COMMITTED 或 DONE；
- 当前 binary/source 对齐；
- 没有未解释的失败；
- 没有未处理的 BLOCKED。

以下不算完成：

- 只有代码提交；
- 只有测试提交；
- 只有 Agent 自报 PASS；
- 只有人工待验但没有自动验证；
- 状态写成 DONE 但工作区仍有未解释修改；
- 使用旧 binary 得到的结果。

### 3.2 按批次触发

以下事件发生时，立即治理审计：

- R19.21 或任何新批次全部结束；
- 进入新的 Architecture Lane 阶段；
- 开始后台生成、异步 meshing、EntityStore、存档迁移或网络开发；
- 改变核心接口；
- 改变 Chunk 生命周期；
- 改变测试矩阵结构；
- 改变 Renderer 后端；
- 改变存档格式；
- 改变网络协议。

### 3.3 按时间触发

即使没有完成 5 个任务，每周也至少审计一次。

默认时间：

- 每周一；
- 本地时间 09:00；
- 项目 QtMinecraft；
- 无重大变化时静默完成；
- 只有发现漂移、失败、阻塞或需要人工决策时报告。

### 3.4 按异常触发

以下情况不等待 5 个任务，立即触发审计：

- 同一根因连续失败 2 次；
- 完整矩阵耗时增长超过基线 20%；
- 主线程或内存指标增长超过基线 20%；
- 出现 stale binary；
- PASS 数增加但测试覆盖明显变弱；
- 阴性轮不再能抓到回退；
- docs 数字和真实日志不一致；
- 工作区出现未知修改；
- Agent 修改了治理文档或验收条件；
- 任务连续扩大范围；
- 单个任务超过预估范围两倍。

## 4. 治理审计流程

每次治理审计严格执行以下步骤。

### Step 1：读取短状态

先读取：

1. docs/agent-state.md，如果存在；
2. dev-plan 顶部 Current Control Block；
3. docs/agent-continuation-prompt-2026-09-08.md；
4. 本治理文档。

不允许第一步就全文阅读 dev-plan 或 refactor-plan。

### Step 2：确定审计窗口

以以下对象作为窗口：

- 上一次治理审计 commit；
- 上一次治理审计日期；
- 最近 5 个已完成任务；
- 当前未完成任务；
- 当前批次；
- 最近 20 条 Git 提交。

如果没有上次治理记录，则从最近 5 个任务开始。

### Step 3：检查 Git 事实

检查：

- 当前 branch；
- HEAD；
- 最近提交顺序；
- fix/test/docs 是否成对；
- 是否存在未提交修改；
- 未提交修改是否属于当前任务；
- 是否有用户修改被误认为 Agent 修改；
- 是否出现大范围无关文件变化；
- 是否出现 build、logs、saves 或资源误提交。

### Step 4：检查任务账本

检查：

- 当前任务是否唯一；
- READY 任务是否有依赖；
- DONE 任务是否真的有证据；
- BLOCKED 是否被重复尝试；
- 下一任务是否合理；
- 任务是否越来越大；
- 是否只做 Gameplay Lane 而 Architecture Lane 停滞；
- 是否只做架构而长期没有可玩结果；
- 是否存在重复任务或编号冲突。

### Step 5：检查架构方向

对照 docs/refactor-plan-2026-09-08.md，只检查与当前阶段相关的章节：

- 是否仍然以 C++ headless simulation 为核心；
- 是否继续扩大 QML 对模拟的职责；
- 是否继续让 World 直接依赖 Renderer；
- 是否出现 worker 直接操作 QObject 或 QQuick3D；
- 是否出现新的全局状态；
- 是否出现第二套权威规则；
- 是否在没有 Chunk lifecycle 的情况下继续扩大世界；
- 是否在没有稳定 snapshot 的情况下开始联机；
- 是否在没有 EntityStore 的情况下继续增加大量 QML 实体；
- 是否开始改变存档格式但没有 SaveCoordinator。

### Step 6：检查质量

检查：

- 当前任务是否有正向测试；
- 是否有阴性轮；
- 是否记录退出码；
- 是否验证 binary/source 对齐；
- 是否有未解释 warning；
- 是否有 flaky 统计；
- 测试是否通过放宽 envelope 变绿；
- 是否删除、跳过或弱化了测试；
- docs 中的 PASS 数是否有真实日志；
- 人工待验是否被正确标记。

### Step 7：检查方向收益

每个最近任务都回答：

1. 它是否解决了用户目标；
2. 它是否增加了未来重构的阻力；
3. 它是否建立了可复用的 Module；
4. 它是否减少了重复权威；
5. 它是否改善了可测试性；
6. 它是否让后续后台、联机或移动端更容易；
7. 它是否只是增加了更多特殊分支。

如果连续 3 个任务只增加特殊分支而没有增加可复用结构，创建架构纠偏任务。

### Step 8：输出治理结论

每次审计只能得出以下三种结论之一：

- GREEN：方向正确，可以继续；
- YELLOW：方向基本正确，但必须先完成纠偏任务；
- RED：方向、状态或证据存在高风险，必须暂停。

## 5. 治理结论和自动动作

### 5.1 GREEN

条件：

- 当前架构方向没有明显漂移；
- 当前任务证据完整；
- 测试和 binary 对齐；
- 没有未知工作区修改；
- 没有高严重度回归；
- 下一任务依赖满足。

动作：

1. 更新治理审计日期；
2. 更新 last governance commit；
3. 把下一任务保持为 READY；
4. 继续普通开发循环；
5. 如果审计由定时任务触发且项目空闲，可以认领下一个 READY 任务。

### 5.2 YELLOW

条件：

- 存在低或中严重度方向问题；
- 可以在既有目标和既有验收条件内修复；
- 不涉及不可逆数据变化；
- 不需要新的产品决定。

动作：

1. 写入治理报告；
2. 在 dev-plan 中创建 GOV 纠偏任务；
3. 将纠偏任务设为 P0 或 P1；
4. 暂停新的低优先级玩法任务；
5. 先完成纠偏任务；
6. 重新执行正向、阴性和回归测试；
7. 治理重新判定为 GREEN 后继续原队列。

允许的 YELLOW 自动纠偏例子：

- 文档和真实矩阵数字不一致；
- 当前任务忘记回标；
- 测试 binary 过期；
- 缺少一个已经明确的回归测试；
- 一个模块出现明显重复权威；
- 已确定的接口命名或目录迁移；
- 任务过大但可以安全拆分；
- 缺少恢复点或下一任务。

### 5.3 RED

条件：

- 产品目标出现歧义；
- 架构北极星需要改变；
- 需要修改验收条件才能通过；
- 需要删除或弱化测试；
- 需要不可逆存档迁移；
- 可能覆盖用户数据；
- 出现未归属的工作区修改；
- 同一根因连续 3 次失败；
- 性能退化超过基线 20% 且根因不明；
- 出现潜在数据丢失；
- 网络协议或存档格式需要重大决策；
- 发现 IP 或第三方资产分发风险。

动作：

1. 停止自动代码修改；
2. 把当前任务设为 NEEDS_HUMAN 或 BLOCKED；
3. 写清事实、风险和候选方案；
4. 不自动改变长期计划；
5. 不自动合并；
6. 等用户或明确的预授权规则。

如果用户预先授权了某种固定处理方式，必须把授权写入本治理文档的新版本，而不是让 Agent 从聊天记忆中猜。

## 6. 自动纠偏边界

### 6.1 可以自动做

- 重新构建过期 binary；
- 重跑已有测试；
- 修复明确的测试 harness 错误；
- 增加缺失的回归测试；
- 创建和拆分任务；
- 更新事实性 docs；
- 修复格式和状态字段；
- 将失败分类；
- 将重复任务合并；
- 为已明确的接口添加 Adapter；
- 在既有验收条件内修复实现；
- 为任务补充恢复点；
- 继续下一个已满足依赖的 READY 任务。

### 6.2 不可以自动做

- 修改总体产品目标；
- 修改北极星架构；
- 降低验收标准；
- 删除或跳过失败测试；
- 修改阴性轮使其失去敏感性；
- 删除用户未提交代码；
- 进行不可逆存档迁移；
- 覆盖损坏存档；
- 自动合并有争议的分支；
- 改变网络协议兼容规则；
- 改变方块、实体或生存机制的产品口径；
- 为了性能大幅降低质量但不记录取舍；
- 把人工待验标成已验；
- 把 self-reported 标成 independently verified。

### 6.3 自动修复的最小原则

自动修复必须满足：

- 目标不变；
- 验收不变；
- 数据格式不变，或已有明确迁移规则；
- 影响范围可解释；
- 有正向测试；
- 有回归测试；
- 有回滚方式；
- 失败后可以恢复到上一个 commit。

- 结论；
- 下一触发点。

## 8. 每 5 个任务的计数规则

Agent 不要依赖矩阵 PASS 数量判断完成了多少任务。

任务计数来源按优先级为：

1. dev-plan 中明确的 COMMITTED/DONE 任务；
2. Git 中带任务编号的 fix/test/docs 闭环；
3. 治理报告中记录的完成任务；
4. 矩阵 PASS 增量只能作为辅助证据。

例如：

    t1021：fix + test + docs = 1 个完成任务
    t1022：fix + test + docs = 1 个完成任务
    t1023：fix + test + docs = 1 个完成任务
    t1024：fix + test + docs = 1 个完成任务
    t1025：fix + test + docs = 1 个完成任务
    到达 5 个 → 触发治理审计

如果一个任务有多个 fix commit，只计 1 个任务。

如果一个 fix 没有 test 或 docs，不计入完成数。

## 9. 定时审计与正常开发的关系

定时审计不是另一个无限开发 Agent，而是一个治理恢复器：

1. 读取本治理文档；
2. 检查当前控制块；
3. 检查最近任务和 Git；
4. 检查方向；
5. 没有问题时继续当前 READY 任务；
6. 发现 YELLOW 时先创建并完成纠偏任务；
7. 发现 RED 时安全停止并保留恢复点；
8. 不重复已经完成的任务；
9. 不全文阅读所有历史文档；
10. 只在有意义变化、失败或需要决策时通知。

主 Agent 和治理 Agent 可以是同一个模型，也可以不同：

- GLM5.3Flash 负责日常实现；
- 治理 Agent 负责周期审计；
- 治理 Agent 不应因为模型不同就改变事实优先级；
- 两者都必须遵守本文件。

如果同一个 Agent 同时负责实现和审计，必须保持“先实现、后独立审计”的顺序，不能在尚未完成实现时自己宣布 GREEN。

## 10. 断链恢复

定时审计或主开发 Agent 中断后，恢复顺序为：

1. 读取 agent-continuation-prompt；
2. 读取 agent-state 或 dev-plan 控制块；
3. 读取最近一份治理报告；
4. 查看 Git 状态；
5. 查看最近任务；
6. 查看源码和 binary 时间戳；
7. 判断是继续、重试、恢复工作区还是暂停；
8. 只读取当前任务和治理窗口相关的长文档片段。

如果中断发生在治理审计中：

- 治理状态保持 IN_PROGRESS；
- 不把审计写成 GREEN；
- 下次从审计起点重新核对；
- 不重复修改已经提交的代码。

如果中断发生在纠偏任务中：

- 纠偏任务保持 IN_PROGRESS；
- 不继续普通低优先级任务；
- 先完成纠偏闭环。

## 11. 长期防跑偏指标

每次治理审计至少观察以下指标：

| 指标 | 健康状态 |
|---|---|
| fix/test/docs 闭环率 | 接近 100% |
| 未提交修改 | 可解释 |
| stale binary | 0 |
| 阴性轮异常 | 0 或已登记 |
| 重复失败根因 | 不超过 2 次 |
| flaky 测试 | 有复现率和台账 |
| 任务平均范围 | 不持续扩大 |
| Main.qml 新增游戏逻辑 | 逐步减少 |
| World 对 Renderer 直接依赖 | 不增加 |
| QML 实体 Delegate 数量 | 不随实体总数线性增长 |
| 架构 Lane 进度 | 不连续两个批次停滞 |
| 性能基线 | 无未解释的 20% 以上退化 |
| 文档和真实日志 | 一致 |
| 人工待验 | 有清单，不被伪完成 |

如果某项连续两次治理变差，自动创建对应纠偏任务。

## 12. 当前实际执行建议

在这个治理机制生效后，当前项目按以下顺序运行：

1. 恢复和完成当前 t1025；
2. 完成 t1025 的 fix/test/docs；
3. 触发或手动执行一次治理审计；
4. 如果 GREEN，继续 t1026；
5. 完成 5 个任务后再次治理；
6. R19.21 结束后执行批次治理；
7. 建立 R20.01 至 R20.04 的 Agent 控制面；
8. 进入 R20.05 基础类型重构；
9. 每个架构阶段完成后执行治理；
10. 进入异步生成、异步 meshing、EntityStore、存档和联机阶段时强制审计；
11. 定时任务作为主 Agent 断链后的恢复器和方向检查器。

不要因为有了定时任务就让主 Agent 同时开多个写入进程。默认仍然是一个项目、一个工作区、一个写入 Agent、一个串行任务。

---

## 13. 最终原则

长期自动开发的核心不是让 Agent “永远不停止”，而是让它：

- 停下时知道为什么停；
- 下次知道从哪里继续；
- 继续前知道当前代码是否新；
- 修复前知道哪个 Module 是权威；
- 测试后知道证据是否真实；
- 方向漂移时能够尽早发现；
- 失败重复时能够停止；
- 不会通过修改验收标准来伪造成功；
- 在允许范围内自动纠偏；
- 在不允许范围内安全等待决定。

本项目可以长期保持自动开发，但“产品方向”和“不可逆动作”的最终责任不能由 Agent 自己循环授权给自己。

执行循环负责速度，治理循环负责方向，Git 和文档负责记忆，测试负责证据。
